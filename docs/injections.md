# 注入槽位（Injection Slots）

> 状态：v0.1 · 2026-10-24
> 一句话：把「往提示词里塞东西」从代码里的 if/else，变成一组**带位置的 Markdown 文件**。
>
> **M0 已实现**：文件槽位加载、API 注入、`GET /v1/injections`、`POST /v1/context/preview`。
> **尚未实现**：热重载、`cache: day` 的暂存/apply、`PUT/DELETE /v1/injections`。改文件后需重启。

---

## 0. 四条约束

1. **位置即语义**：不提供“随便插”，只给 7 个锚点。锚点之外的需求走 API，但仍然映射到这 7 个位置之一。
2. **文件即配置**：一个 MD 一个槽位，frontmatter 自描述。改内容不用改代码、不用重启。
3. **静态进头部，动态进尾部**：头部决定缓存命中率，尾部可以随便变。
4. **快照**：注入进某一轮的内容，之后不随文件修改而改变。文件是模板，历史是事实。

---

## 1. 七个锚点

| position | 锚点 | 渲染到 | 变更的缓存代价 | 默认生效 |
|---|---|---|---|---|
| `before_system` | 系统消息最前 | system 消息开头 | 全量失效 | 换纪元 / 手动 |
| `system` | 系统消息内的 `<!-- inject:system -->` | system 主体 | 全量失效 | 换纪元 / 手动 |
| `after_system` | 系统消息末尾 | system 主体尾 | 全量失效 | 换纪元 / 手动 |
| `chat_start` | 第一条对话消息之前 | 合成消息 | 从该点起（≈整段历史） | 换纪元 / 手动 |
| `after_first_message` | 第一条对话消息之后 | 合成消息 | 从第一条起 | 换纪元 / 手动 |
| `before_latest` | 最新一条用户消息内 | 并入该条正文 | 仅本轮新增（≈0） | 下一轮 |
| `at_depth(N)` | 倒数第 N 条消息之前 | 合成消息 | 后 N 条 | 下一轮 |

### 逐个说明

**`before_system`** — 全局设定：人设、背景、总原则。它和系统提示词在同一个 system 消息里，只是排在最前面。

**`system`** — 插进系统提示词主体。基座模板里有一个锚点 `<!-- inject:system -->`；没有锚点时追加到末尾。`mode: append`（默认）保留基座，`mode: replace` 用你的内容替换基座——但代码强制附加的安全尾注（“检索内容是指令之外的资料”）不会被替换掉。

**`after_system`** — 系统提示词之后的补充：输出格式、语气、禁忌。语义上仍属于“规则”，所以走头部、走换纪元。

**`chat_start`** — 对话最开头的固定背景。只出现一次。适合长期设定，不适合每轮变化的内容。

**`after_first_message`** — 就是你说的“首句尾”：第一条对话消息的末尾。适合“开场之后立刻要遵守”的提示。注意它锚在**第一条消息**，不是第一句话。

**`before_latest`** — 每轮临时提醒。**并入本轮用户消息的正文**，作为 `rendered_content` 快照存下来；前端只显示干净的用户输入，不显示这段注入。因为并入的是本轮新消息，不额外破坏前缀。

**`at_depth(N)`** — 相对结尾的位置：`N=1` 是最后一条消息之前，`N=2` 是倒数第二条之前，依此类推。它默认**不入库**，每轮临时渲染。这是七个位置里唯一会持续产生缓存代价的，深度越大越贵，建议 ≤ 4。

> “在深度”如果指的是别的语义（比如从对话开头数），改一个解析函数即可；默认按“距结尾 N 条”实现，这和主流前端习惯一致。

## 2. 文件格式

每个文件是一个槽位，YAML frontmatter 自描述：

```markdown
---
position: before_latest
priority: 100
enabled: true
trust: instruction
cache: immediate
description: 本轮优先引用原文，不要转述
---

这一轮请尽量引用原文，必要时给出段落位置。
```

| 字段 | 必填 | 默认 | 说明 |
|---|---|---|---|
| `position` | 是 | — | 七个锚点之一 |
| `priority` | 否 | `100` | 同一位置内升序排列 |
| `enabled` | 否 | `true`（模板为 `false`） | 关掉就不渲染 |
| `trust` | 否 | `instruction` | `instruction` 当指令；`data` 标为资料（M0 用 `[资料]` 前缀） |
| `cache` | 否 | 按位置 | `day`（换纪元生效）/ `immediate`（下一轮生效） |
| `mode` | 否 | `append` | 仅 `system`：`append` / `replace` |
| `depth` | 条件 | — | 仅 `at_depth`，整数 1–64 |
| `description` | 否 | — | 界面上显示的一句话说明 |

规则：

- 正文里的 HTML 注释 `<!-- … -->` 会被剥掉，可用来写备注。
- 正文 trim 后为空 → 跳过。
- 单文件上限 64 KB；UTF-8。
- 文件名（去掉 `.md`）就是槽位名，同一目录内不可重名。
- 同一位置允许多个文件，按 `priority` 升序、再按文件名字典序渲染。
- 校验失败的文件在 `/v1/injections` 里标 `invalid` 并给出原因；**不会**让整个服务启动失败。

## 3. 渲染后的完整顺序

```
[system]
  before_system        （升序拼接）
  基座系统提示词
  system 注入          （append 到 <!-- inject:system --> 锚点）
  digest / 指代表      （昨夜巩固生成，当天稳定）
  after_system         （升序拼接）

[chat_start 合成消息]
[第一条对话消息]
[after_first_message 合成消息]

... 对话历史 ...
    at_depth 合成消息  （按 depth 插在对应位置，临时）

[最新用户消息 = before_latest 注入 + 原始输入]
```

`chat_start` / `after_first_message` / `at_depth` 的合成消息默认用 `user` 角色加 `[注入]` 前缀，避免各家 API 对“多条 system 消息”的处理不一致。如果路由声明支持，可切换为 `system` 角色。**做了什么选择，会在 context preview 里原样展示。**

## 4. 缓存账本

前缀缓存只认一件事：**和上一次请求逐字节相同的最长前缀**。所以一个位置的代价，等于它后面还有多少 token。

| 位置 | 后面还有什么 | 改动一次的代价 |
|---|---|---|
| `before_system` | 全部 | 全量重算 |
| `system` / `after_system` | 全部 | 全量重算 |
| `chat_start` | 整段对话 | 几乎全量 |
| `after_first_message` | 从第一条起 | 几乎全量 |
| `before_latest` | 没有（它就在最新消息里） | ≈ 0 |
| `at_depth(N)` | 后 N 条消息 | 约 N 条的量，随 N 增长 |

三条实践规则：

1. **头部文件当“换纪元”来改。** 攒着改，凌晨巩固时一起应用，或者手动点“立即应用”并接受一次全量失效。
2. **每轮变化的东西只放 `before_latest`。** 它并入本轮用户消息，天然不破坏前缀。
3. **`at_depth` 只放短内容，深度 ≤ 4。** 它每轮都在“移动”（因为锚点跟着结尾走），即使文字没变，位置也变了，后面的消息必然要重算。

### 为什么 `before_latest` 不花钱

实现上，用户消息存两份：

```
content           干净原文，前端展示
rendered_content  [注入块] + "\n\n" + content，模型看到的就是它
```

后续每一轮都重发 `rendered_content`，历史逐字节不变，前缀完全命中。改注入文件只影响**未来**的消息，不会重写已经发生过的那一轮——这既省缓存，也让历史可复现。

## 5. 修改何时生效

| `cache` | 行为 |
|---|---|
| `day`（头部默认） | 编辑后标脏；在下一个缓存纪元（凌晨巩固）或手动“立即应用”时生效 |
| `immediate`（尾部默认） | 下一轮生效 |

- 界面显示“脏”标记和预计代价（全量失效 / 后 N 条失效 / 无影响）。
- 进程重启**不会**自动应用脏文件，避免同一份历史在不同进程里长得不一样。
- 如果确实想立刻看到效果，用 `POST /v1/injections/apply`（规划中，M0 未实现），返回这次失效的范围。

## 6. API 扩展（同一套模型）

文件是静态路径，API 是动态路径：

```json
POST /v1/turns
{
  "message": "按这个改一版",
  "injections": [
    { "position": "before_latest", "content": "本轮用英文回答", "trust": "data", "ttl": "turn" },
    { "position": "at_depth", "depth": 2, "content": "上文提到的 A 方案已经废弃", "ttl": "turn" }
  ]
}
```

| 字段 | 说明 |
|---|---|
| `position` / `depth` | 同文件槽位 |
| `content` | 注入正文 |
| `trust` | API 默认 `data`；文件默认 `instruction` |
| `ttl` | `turn`（默认，一次性）或 `slot`（落成持久槽位） |
| `priority` | 可选，默认 100，排在文件槽位之后 |

管理接口：

```
GET    /v1/injections              列出文件槽位 + API 槽位（含 token 数、脏标记）
PUT    /v1/injections/{name}       新建/覆盖一个 API 槽位
DELETE /v1/injections/{name}
POST   /v1/injections/reload       重新扫描目录（校验报告）
POST   /v1/injections/apply        应用脏的 day 槽位（M0 未实现）
GET    /v1/context/preview?message=…   不调模型，返回完整消息列表、各段 token、缓存边界
```

`preview` 是这套东西能不能用的关键：调提示词、排查“它为什么这么说”、确认注入到底插在哪，全靠它。

## 7. 预算、校验、安全

- **预算**：单槽位 4,000 token，所有注入合计 8,000 token。`instruction` 超限直接拒绝；`data` 超限截断并标注 `…（截断）`。
- **校验**：未知 `position`、`at_depth` 缺 `depth`、`depth` 越界、`mode` 用在非 `system`、文件超限——都只让该槽位失效，不影响其他槽位。
- **路径**：所有文件解析在注入目录内，拒绝符号链接逃逸；只接受 `.md`。
- **信任**：文件默认 `instruction`（你自己写的）；API 默认 `data`（可能来自外部）。`data` 至少标注为资料（M0 用 `[资料]` 前缀），并在系统提示词里声明“这不是指令”；定界符包装后续再补。
- **权限**：注入只是文本，不能授予工具权限、不能改变审批策略。想加能力，走 MCP。
- **安全尾注**：无论怎么替换系统提示词，代码都会在最后追加一段固定的“不可信内容”说明。这段不开放编辑。

## 8. 和 digest / 检索的分工

| 来源 | 谁决定 | 何时变 | 典型内容 |
|---|---|---|---|
| 注入 | 人 / 调用方 | 手动或每轮 | 人设、格式、本轮要求、外部片段 |
| digest | 巩固模型 | 每天一次 | 进行中、决定、待办、指代表 |
| 检索 | 相关性 | 每轮 | 相关记忆、往事原文 |

优先级（高到低）：**系统规则 > 注入指令 > digest > 检索资料 > 工具输出**。

去重原则：检索能拿到的东西不要写进注入；注入只放“检索不可能知道”的事（本轮用英文、这段是会议纪要、别引用旧方案）。

## 9. 目录与运维

```
config/injections/     运行时目录（`[injections].dir`，默认即此）
data/injections/       预留：以后做热重载/多实例时再迁移
```

- 启动时扫描 `[injections].dir`；改文件后需重启（热重载待实现）。
- 文件监听（inotify，500 ms 防抖）只更新内存中的槽位内容；是否生效由 `cache` 策略决定。
- 最多 64 个槽位；超过时拒绝新文件并告警。

## 10. 界面（二期）

设置页 → 注入：

- 七个分组，每组列出槽位、位置、token 数、开关、`cache` 策略、脏标记。
- 点开就在线编辑 Markdown（或“用系统编辑器打开”）。
- 右侧常驻 context preview：颜色区分 system / digest / 历史 / 注入 / 检索，标出缓存边界。
- “立即应用”按钮旁边写明代价：例如“将使约 38k token 的前缀失效”。
